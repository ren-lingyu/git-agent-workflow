#+TITLE: Git Agent Workflow (GAW)
#+AUTHOR: Lingyu Ren

* Git Agent Workflow
Git Agent Workflow (GAW) is a Git-native workflow for maintaining persistent
agent working state and history alongside a Git repository.

GAW is intended for coding workflows in which an agent may work on a project
across many independent sessions.  Instead of treating one long-lived model
context as the primary store of working state, GAW keeps selected agent state
in Git and lets Git provide its history and reachability model.

* Status
The current release is =0.2.0=.  It adds repository lifecycle operations to
the daily runtime introduced in 0.1.0.  A new repository can be initialized
with =git gaw init=, an existing local GAW branch can be materialized with
=git gaw deploy=, and registered branches can be renamed or safely deleted
with =git gaw branch=.  The =check=, edit, stage, =commit=, and =show= loop and
local ref-transaction protection remain the normal daily interface.

The repository protocol and user-facing interface may still change before a
stable release.  Remote-side enforcement, automatic fetching, arbitrary
corruption repair, and system-wide deployment integration remain out of scope.

* Installation
GAW currently supports =x86_64-linux= and requires Nix with flakes enabled.
Git 2.54 or newer is required for the configured hook support used by branch
protection.

Build the default package from a checkout:

#+begin_src sh
nix build .#default
./result/bin/git-gaw --help
#+end_src

The executable must be available on =PATH= under the name =git-gaw= for Git to
discover it as the =git gaw= subcommand:

#+begin_src sh
git gaw --help
#+end_src

The flake also exports the package as =packages.x86_64-linux.default= and as
=git-agent-workflow= through its default overlay.  Building and testing do not
provision a GAW worktree or modify repository-local hook configuration.

* Design
** Separate GAW History
GAW history is an independent Git history rather than a history derived from
the ordinary project branches.

A GAW commit records the state of the GAW workspace in its own tree.  Its
parents have two distinct roles:

1. the first parent is the previous GAW commit;
2. any additional parents are project commits associated with that GAW state.

The trees of additional project parents are not merged into the GAW tree.
They are parent edges used to associate project snapshots with agent history
and to keep those commits reachable through ordinary Git object reachability.

The canonical temporal history of GAW is therefore its first-parent chain.

** Portable and Local State
The portable truth of a GAW branch is its ordinary Git branch representation,
commit history, =.gaw/config=, and workspace state.  Remote transport uses
ordinary branch history; GAW does not require =refs/gaw/*= to be pushed or
fetched.

The =refs/gaw/*= namespace is rebuildable local deployment metadata:

#+begin_src text
refs/gaw/heads/<name> -> refs/heads/<name>
refs/gaw/HEAD         -> refs/gaw/heads/<name>
#+end_src

The first symbolic ref records local GAW membership for validation and branch
protection.  The second is a persisted local selector.  It is not portable
remote state and is not authoritative for =git gaw commit=, which uses the
current worktree's symbolic =HEAD=.  Rebuildable means that no irreplaceable
repository information lives in this namespace; it does not authorize runtime
commands to repair malformed metadata automatically.

** Workspace
GAW manages a selected set of paths as its workspace.

The workspace does not need to be one directory and may consist of multiple
files and directories.

Workspace contents are intentionally opaque to GAW.  GAW manages their Git
history and validates the surrounding repository protocol, but does not
prescribe their internal format.

** Configuration
The current GAW workspace declaration is stored as a =100644= blob at
=.gaw/config= in the active independent GAW history.  The bootstrap schema is
intentionally unversioned:

#+begin_src lisp
(:workspace
 ((:file "AGENTS.md")
  (:directory "notes")))
#+end_src

Workspace paths are literal repository-root-relative Git paths.  They use
=/= as their component separator, are not silently normalized, and may not
contain =.= or =..= components.  The repository-root =.gaw= namespace and
every =.git= component are reserved.

The Common Lisp entry point =(git-agent-workflow.config:read-config
directory)= resolves the current GAW source ref to an immutable commit ID,
reads the blob as exact bytes, strictly decodes UTF-8, and validates a
restricted S-expression grammar and schema.  It does not inspect current
worktree path kinds; that matching belongs to later workspace operations.
The API layer resolves the current source ref and supplies the fixed config
path and resource limits as explicit runtime arguments; runtime and core do
not read those defaults from package-level state.

The related entry point =(git-agent-workflow.config:read-config-at-tree
directory tree-oid)= accepts a full tree object ID.  It is used when a staged
tree must be validated before a commit makes it reachable.
=(git-agent-workflow.config:read-config-blob directory blob-oid)= provides the
same strict parsing for an already resolved immutable config blob, allowing an
index consumer to parse one coherent index snapshot without rereading it.

** Project Association
A GAW commit may be associated with zero, one, or multiple project commits.

These associations are represented directly as additional Git parent edges
rather than through a separate snapshot database or identifier scheme.

A project commit attached to GAW history must not itself track the GAW
workspace or reserved GAW protocol paths.  This is a local validity condition
on commits that participate in GAW history rather than a repository-wide
restriction on unrelated branches.

** Initializing a Repository
=git gaw init= creates initial GAW history and immediately uses the normal
deployment path:

#+begin_src text
git gaw init --branch <name> [--worktree-path <path>]
#+end_src

It first performs read-only checks for existing valid or GAW-like history,
local protocol metadata, hook conflicts, and an obvious requested worktree
path conflict.  A branch containing a valid committed GAW state means the
repository is already initialized.  A branch with a =.gaw/config= marker that
fails complete committed-state validation is treated as ambiguous or corrupt,
not ignored.

The initial =(:workspace ())= blob, its trees, and the root commit are written
before any ref becomes visible.  The source branch, its exact symbolic
registration, and =refs/gaw/HEAD= are then created in one expected-state
=update-ref --stdin= transaction.  A failed ref transaction may leave
unreachable objects but cannot leave a partially created ref graph.  The root
commit message is =Initialize GAW= and its author and committer are =Git Agent
Workflow <gaw@invalid>=; inherited signing configuration is not used.

** Deploying Local State
=git gaw deploy= materializes local metadata and optional worktree state for
history already present in a local ordinary branch:

#+begin_src text
git gaw deploy [--branch <name>] [--worktree-path <path>]
#+end_src

With =--branch=, the named =refs/heads/*= branch must already exist and pass
complete committed-state validation.  Without it, a valid =refs/gaw/HEAD= is a
fast path.  If the selector is missing, deploy enumerates local branches,
uses the fixed =<branch>:.gaw/config= path only as a cheap prefilter, and then
fully validates every matching candidate.  Zero candidates fail; multiple
candidates require =--branch=.  Malformed existing local registration or
selector state is corruption and is never overwritten.

Deploy does not fetch, contact remotes, or create a missing source branch.  It
creates or validates the exact local symbolic registration and selector,
reconciles the requested linked worktree, verifies an attached worktree with
=git gaw check=, and installs the canonical repository-local configured
protection hook.  Repeating deploy against the same valid state is safe.

** Registered Branch Lifecycle
Operations that must coordinate an ordinary source branch with local GAW refs
are exposed through:

#+begin_src text
git gaw branch -m <new-name>
git gaw branch -d <name>
#+end_src

Rename operates on the registered GAW branch checked out by the current
worktree.  It uses native =git branch -m= so Git maintains worktree =HEAD=,
reflogs, and branch configuration, then atomically moves the registration and
selector and verifies the final invariant.

Delete accepts only a branch with an exact local registration.  It uses native
=git branch -d=, retaining Git's checked-out-branch and safe-delete checks,
then removes the registration and the selector when it selected that branch.
Unregistered branches remain native Git's responsibility.  Because native
branch operations and protocol-ref changes cannot share one transaction, both
operations use strict preflight checks, ordered updates, and best-effort
compensation.  Incomplete compensation is reported explicitly as a partial
failure.

** Creating Commits
The command =git gaw commit= creates commits on the registered GAW branch
checked out by the current worktree.  It must be run at that worktree's root.
The worktree's symbolic =HEAD= is authoritative; =refs/gaw/HEAD= does not
select the branch for this command.

The command uses the current index as its complete tree source.  It neither
stages paths nor includes unstaged or untracked changes.  A candidate tree is
accepted only when it contains a valid =.gaw/config= and no content outside
=.gaw= and the declared workspace.  Gitlinks are not supported in a GAW tree.

The command syntax is:

#+begin_src text
git gaw commit [--allow-empty] [--allow-empty-message]
               (-m <message> | -F <file>)...
               [--] [project-commit...]
#+end_src

Message options may be repeated and mixed.  =-m= values are encoded as UTF-8;
=-F= files and =-F -= standard input are read as exact bytes.  With no project
commit, an unchanged tree is rejected unless =--allow-empty= is present.  A
commit with project parents is meaningful even when its tree is unchanged.

Each project revision is resolved once to a commit object.  Its tip tree is
checked locally against the candidate workspace declaration and the reserved
=.gaw= namespace; its ancestors are not scanned.  The project commits then
become additional parents in command-line order.  Their trees are never
merged into the GAW tree.

Git subprocesses ignore inherited =GIT_*= and =EMAIL= variables and ignore
system and user Git configuration.  Repository and worktree configuration is
retained only for repository interpretation.  GAW always records both author
and committer as =Git Agent Workflow <gaw@invalid>=, and supplies that identity,
UTC timestamps, message, hook policy, and unsigned commit policy explicitly.
The branch ref is updated with an expected-old-object check so a concurrent ref
change is never overwritten.

When branch protection is configured, the final ref update disables only the
=gaw-reference-transaction= named hook.  Other configured hooks remain enabled.
The existing suppression of traditional hooks through =core.hooksPath= is a
separate commit policy and is not the branch-protection bypass mechanism.

** Protecting Registered Branches
GAW can use Git 2.54's configured =reference-transaction= hook to prevent
ordinary Git commands from modifying a registered GAW branch.  Protection is
installed or validated by =git gaw init= and =git gaw deploy=.  Its canonical
repository-local configuration is:

#+begin_src sh
git config --local hook.gaw-reference-transaction.event reference-transaction
git config --local hook.gaw-reference-transaction.command \
  'git-gaw --reference-transaction'
git config --local hook.gaw-reference-transaction.enabled true
#+end_src

The machine-facing option is intentionally absent from command help.  During
the =preparing= phase it checks direct =refs/heads/*= updates.  For object
updates through a symbolic ref such as =HEAD= or a registration ref, it also
resolves the symbolic chain to determine which branch Git will actually
modify.  Switching a worktree's =HEAD= between branches remains allowed when
it does not move a registered branch.  The hook rejects the complete ref
transaction when the resulting branch has an exact =refs/gaw/heads/*=
symbolic registration, and it also rejects ordinary transactions which
directly create, modify, or delete any =refs/gaw/*= protocol ref.  A registration
continues to protect its branch name when the branch itself is missing.
Malformed transaction input, an invalid registration, or a failed
registration query is rejected rather than treated as safe.  The =prepared=,
=committed=, and =aborted= phases perform no work; unknown phases are protocol
errors.

An object update addressed through a symbolic registration is also rejected
when Git would dereference it and modify the protected branch.  Valid GAW
commit and lifecycle operations perform their own validation and disable only
this named hook for guarded ref mutations; unrelated configured hooks remain
enabled.  Divergent or incomplete configuration is reported as a deployment
conflict rather than silently overwritten.

This hook is a local guard against accidental ref updates, not an authorization
boundary.  A user who controls the repository can disable its configuration or
modify ref storage directly.

** Showing History
The command =git gaw show= delegates object display and formatting to =git
show= while enforcing the canonical GAW history semantics:

#+begin_src text
git gaw show [git-show-options] [object-or-range...] [-- pathspec...]
#+end_src

History traversal follows only first-parent edges, and a merge commit's patch
is generated only against its first parent.  Options such as =--stat=,
=--name-only=, =--format=, =--no-patch=, and pathspecs retain their native Git
meaning.  Merge display modes that compare the result with additional parents,
including =-m=, =-c=, =--cc=, and =--remerge-diff=, are rejected.

=--no-diff-merges= and the equivalent =--diff-merges=off= and
=--diff-merges=none= remain available when only commit metadata is wanted.
Explicit object selection also retains its Git meaning, so a user may still
request an associated project commit directly, for example with =HEAD^2=.
Only implicit traversal and the patch base of a selected merge commit are
restricted.

GAW does not currently provide a =diff= subcommand.  Arbitrary tree, index, or
worktree comparisons remain available through =git diff= itself.

The same operation is available to Common Lisp callers as
=(git-agent-workflow.show:show directory arguments)=.  It writes Git's output
directly to the current process streams and returns Git's exit status.

** Checking a Provisioned Worktree
The command =git gaw check= performs a read-only readiness check for an already
provisioned GAW worktree.  It checks the local branch and registration, the
committed config and workspace, additional project-parent tip trees, the
complete staged candidate, and conflicting Git operation state.

The command may run from a subdirectory and reports the resolved worktree root,
although =git gaw commit= must still run at that root.  It does not replace
=git status= or =git diff=: untracked and unstaged changes remain native Git
concerns.  Commit-message validity, command-line project parents, and
=--allow-empty= are also checked only by the particular commit invocation.

Expected readiness failures are aggregated into one report.  The exit status
is zero when the report has no error finding and one otherwise; warnings do not
make the report fail.  The check does not write the index, refs, worktree, or
object database.

** Command Help
GAW provides overview and command-specific help through =git gaw help= and
=git gaw help init|deploy|branch|commit|show|check=.  The
overview is also available as =git gaw --help= or =git gaw -h=, while each
command accepts =--help= as its sole argument.

Help text is maintained as independent UTF-8 plain-text source files.  It is
strictly decoded and embedded when the Lisp system is compiled, so the packaged
executable does not locate or read those source files at runtime.

** Daily Runtime Loop
For a new repository, initialize a source branch and optionally materialize a
linked worktree:

#+begin_src text
git gaw init --branch agents --worktree-path .agents
#+end_src

After cloning history which contains a GAW branch, first ensure the ordinary
source branch exists locally, then deploy it without any implicit network
operation:

#+begin_src text
git gaw deploy --branch agents --worktree-path .agents
#+end_src

Once deployed, the intended daily loop is:

#+begin_src text
git gaw check
edit workspace files
git status / git diff
git add <paths>
git gaw commit [options] [project-commit...]
git gaw show
#+end_src

** History Semantics
The first parent of a GAW commit represents temporal GAW history.

Additional parents represent associated project snapshots and do not
participate in that temporal ordering.

As a result, the canonical history traversal of GAW follows first-parent
edges, and the canonical change represented by a GAW commit is the change
relative to its first parent.

** Git as the History Store
GAW deliberately relies on Git itself for:

- recording commit identity;
- temporal history;
- object storage;
- parent relationships;
- reachability.

In particular, relationships between GAW state and project snapshots are
encoded directly in the Git commit graph rather than duplicated in a
separate metadata database.

* Development
GAW is implemented in Common Lisp and built as an ASDF system.

The build is managed with Nix flakes and =cl-nix-forge=.  The currently
supported system is =x86_64-linux=, and GAW requires Git 2.54 or newer.

Run the complete Common Lisp and Git integration test suite with:

#+begin_src sh
nix flake check
#+end_src

** Package Layout
Source packages are organized as directories under =src/=.  Each package
directory contains its own =package.lisp= and the implementation files owned
by that package.  The top-level =src/package.lisp= defines the
=git-agent-workflow= package; it is intentionally minimal and reserved for a
future unified user-facing API.

Tests follow the same package-oriented layout under =tests/=.  Shared test
support and the top-level test runner remain directly under =tests/=, while
package-specific definitions and tests live in the corresponding package
directory.

** Implementation Layers
Implementation files use the naming pattern =<name>.<layer>.lisp=.  The
available layers have the following responsibilities:

- =*.external.lisp= resolves package-owned external programs from the build
  environment, with source-tree fallbacks.
- =*.core.lisp= contains pure transformations, validation, policy, and data
  definitions.  It does not perform Git I/O or read dynamically bound
  configuration.
- =*.runtime.lisp= performs Git I/O and orchestrates operations using explicit
  arguments and the core layer.
- =*.api.lisp= provides package entry points.  Where configurable defaults
  exist, it converts special variables, external programs, or default
  configuration into explicit arguments for the runtime layer.

The API layer depends on the external and runtime layers; the runtime layer
depends on the core layer.  A package only defines the layers it needs; empty
layer files are not required.

** ASDF Composition
Package directories are represented by ASDF modules with explicit
=:pathname= values.  File-level =:depends-on= declarations encode the layer
order and cross-package dependencies rather than relying on incidental source
file ordering.  The test system uses corresponding modules for tested
packages and dispatches their runners from a top-level test entry point.
