#+TITLE: Git Agent Workflow (GAW)
#+AUTHOR: Lingyu Ren

* Git Agent Workflow
Git Agent Workflow (GAW) is a Git-native workflow for maintaining persistent
agent working state and history alongside a Git repository.

GAW is intended for coding workflows in which an agent may work on a project
across many independent sessions.  Instead of treating one long-lived model
context as the primary store of working state, GAW keeps selected agent state
in Git and lets Git provide its history and reachability model.

* Status
GAW is currently under early development.

The repository currently contains an early Common Lisp implementation and its
Nix build configuration.  The repository protocol and user-facing interface
are still under development and are not yet available for general use.

* Design
** Separate GAW History
GAW history is an independent Git history rather than a history derived from
the ordinary project branches.

A GAW commit records the state of the GAW workspace in its own tree.  Its
parents have two distinct roles:

1. the first parent is the previous GAW commit;
2. any additional parents are project commits associated with that GAW state.

The trees of additional project parents are not merged into the GAW tree.
They are parent edges used to associate project snapshots with agent history
and to keep those commits reachable through ordinary Git object reachability.

The canonical temporal history of GAW is therefore its first-parent chain.

** Workspace
GAW manages a selected set of paths as its workspace.

The workspace does not need to be one directory and may consist of multiple
files and directories.

Workspace contents are intentionally opaque to GAW.  GAW manages their Git
history and validates the surrounding repository protocol, but does not
prescribe their internal format.

** Configuration
The current GAW workspace declaration is stored as a =100644= blob at
=.gaw/config= in the active independent GAW history.  The bootstrap schema is
intentionally unversioned:

#+begin_src lisp
(:workspace
 ((:file "AGENTS.md")
  (:directory "notes")))
#+end_src

Workspace paths are literal repository-root-relative Git paths.  They use
=/= as their component separator, are not silently normalized, and may not
contain =.= or =..= components.  The repository-root =.gaw= namespace and
every =.git= component are reserved.

The Common Lisp entry point =(git-agent-workflow.config:read-config
directory)= resolves the current GAW source ref to an immutable commit ID,
reads the blob as exact bytes, strictly decodes UTF-8, and validates a
restricted S-expression grammar and schema.  It does not inspect current
worktree path kinds; that matching belongs to later workspace operations.
The API layer resolves the current source ref and supplies the fixed config
path and resource limits as explicit runtime arguments; runtime and core do
not read those defaults from package-level state.

The related entry point =(git-agent-workflow.config:read-config-at-tree
directory tree-oid)= accepts a full tree object ID.  It is used when a staged
tree must be validated before a commit makes it reachable.

** Project Association
A GAW commit may be associated with zero, one, or multiple project commits.

These associations are represented directly as additional Git parent edges
rather than through a separate snapshot database or identifier scheme.

A project commit attached to GAW history must not itself track the GAW
workspace or reserved GAW protocol paths.  This is a local validity condition
on commits that participate in GAW history rather than a repository-wide
restriction on unrelated branches.

** Creating Commits
The command =git gaw commit= creates commits on the registered GAW branch
checked out by the current worktree.  It must be run at that worktree's root.
The worktree's symbolic =HEAD= is authoritative; =refs/gaw/HEAD= does not
select the branch for this command.

The command uses the current index as its complete tree source.  It neither
stages paths nor includes unstaged or untracked changes.  A candidate tree is
accepted only when it contains a valid =.gaw/config= and no content outside
=.gaw= and the declared workspace.  Gitlinks are not supported in a GAW tree.

The command syntax is:

#+begin_src text
git gaw commit [--allow-empty] [--allow-empty-message]
               (-m <message> | -F <file>)...
               [--] [project-commit...]
#+end_src

Message options may be repeated and mixed.  =-m= values are encoded as UTF-8;
=-F= files and =-F -= standard input are read as exact bytes.  With no project
commit, an unchanged tree is rejected unless =--allow-empty= is present.  A
commit with project parents is meaningful even when its tree is unchanged.

Each project revision is resolved once to a commit object.  Its tip tree is
checked locally against the candidate workspace declaration and the reserved
=.gaw= namespace; its ancestors are not scanned.  The project commits then
become additional parents in command-line order.  Their trees are never
merged into the GAW tree.

Git subprocesses ignore inherited =GIT_*= and =EMAIL= variables and ignore
system and user Git configuration.  Repository and worktree configuration is
retained for repository interpretation and commit identity.  GAW supplies
author, committer, UTC timestamps, message, hook policy, and unsigned commit
policy explicitly.  The branch ref is updated with an expected-old-object
check so a concurrent ref change is never overwritten.

** History Semantics
The first parent of a GAW commit represents temporal GAW history.

Additional parents represent associated project snapshots and do not
participate in that temporal ordering.

As a result, the canonical history traversal of GAW follows first-parent
edges, and the canonical change represented by a GAW commit is the change
relative to its first parent.

** Git as the History Store
GAW deliberately relies on Git itself for:

- commit identity;
- temporal history;
- object storage;
- parent relationships;
- reachability.

In particular, relationships between GAW state and project snapshots are
encoded directly in the Git commit graph rather than duplicated in a
separate metadata database.

* Development
GAW is implemented in Common Lisp and built as an ASDF system.

The build is managed with Nix flakes and =cl-nix-forge=.  The currently
supported system is =x86_64-linux=.

** Package Layout
Source packages are organized as directories under =src/=.  Each package
directory contains its own =package.lisp= and the implementation files owned
by that package.  The top-level =src/package.lisp= defines the
=git-agent-workflow= package; it is intentionally minimal and reserved for a
future unified user-facing API.

Tests follow the same package-oriented layout under =tests/=.  Shared test
support and the top-level test runner remain directly under =tests/=, while
package-specific definitions and tests live in the corresponding package
directory.

** Implementation Layers
Implementation files use the naming pattern =<name>.<layer>.lisp=.  The
available layers have the following responsibilities:

- =*.core.lisp= contains pure transformations, validation, policy, and data
  definitions.  It does not perform Git I/O or read dynamically bound
  configuration.
- =*.runtime.lisp= performs Git I/O and orchestrates operations using explicit
  arguments and the core layer.
- =*.api.lisp= provides package entry points.  Where configurable defaults
  exist, it converts special variables or default configuration into explicit
  arguments for the runtime layer.

Dependencies flow from =api= to =runtime= to =core=.  A package only defines
the layers it needs; empty layer files are not required.

** ASDF Composition
Package directories are represented by ASDF modules with explicit
=:pathname= values.  File-level =:depends-on= declarations encode the layer
order and cross-package dependencies rather than relying on incidental source
file ordering.  The test system uses corresponding modules for tested
packages and dispatches their runners from a top-level test entry point.
