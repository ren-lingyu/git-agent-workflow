## 1. 开发目标

为 Git Agent Workflow (GAW) 的 archive 工作流建立清晰、稳定、可复用的语义，并引入成熟的元信息描述标准及配套工具。

目标是让 agent 能够：

- 将已经选定的原始材料可靠地保存到 GAW archive。
- 将每次归档组织为独立、自解释的快照。
- 保留原始文件内容及相对目录结构。
- 使用标准格式记录快照及文件的元信息。
- 使用现成工具创建、读取、更新和验证元信息。
- 在需要时描述文件之间的关系。
- 通过 GAW Git 历史保存归档状态及其演化。

优先采用现成标准和工具，不自行设计通用归档格式或元信息解析器。

**本项工作不是为 GAW 开发新的归档管理 CLI。**

当前不得预先将 Data Package 或 RO-Crate 定为唯一方案。必须根据实际对照验证形成最终决策。

标准选择与具体工具实现选择相互独立。允许不同工具分别承担创建、读取、编辑和验证职责。

工具功能、规范兼容性、可靠性及可复现性优先于实现语言偏好。

## 2. Archive 职责边界

### 2.1 基本职责

GAW archive 以独立快照的形式保存已经选定、值得长期保留的历史材料。

典型内容包括：

- 不再存在于普通项目 Git 历史中的实验文件。
- 临时运行程序、查询脚本、日志和结果。
- 重要的退役文档。
- 支持历史决策、故障诊断或迁移过程的原始证据。

Archive 与 memory、skills 的职责保持独立：

- **Memory** 保存当前有效的项目知识和工作状态。
- **Archive** 以快照形式保存选定的历史材料及其描述。
- **Skills** 保存可复用的工作流程。
- **Git / GAW** 保存持久化历史和 checkpoint 之间的关系。

Archive 中的旧文档或脚本不会自动恢复为当前指令或权威知识。

### 2.2 明确的责任分工

| 事项 | 责任方 |
|---|---|
| 判断材料是否值得归档 | Agent 与人类 reviewer |
| 判断是否遗漏重要材料 | Agent 与人类 reviewer |
| 决定归档范围 | Agent 与人类 reviewer |
| 正确捕获已选定文件的字节 | 归档操作与相应工具 |
| 组织和描述归档材料 | 归档格式及工具 |
| 验证元信息结构和引用 | 归档工具 |
| 保存归档历史 | Git / GAW |
| 记录 checkpoint 与项目快照的关联 | GAW commit graph |

不要求 GAW 或归档格式证明：

- 所有值得归档的材料都已被选中。
- 元信息中对历史事件的陈述真实。
- 归档内容足以重现原来的实验。
- 文件之间所描述的领域关系在语义上正确。

这些属于内容选择和审查，而不是格式有效性问题。

尤其需要区分：

- **结构有效性**：元信息满足格式约束，字段和引用具有合法结构。
- **归档内容充分性**：所选择的材料足以保存相关历史事实或实验背景。

工具负责前者；后者由 agent 和人类 reviewer 判断。

不要求归档工具验证未被选择的其他文件是否值得归档。

### 2.3 保真性与 Git 完整性

对首次进入 Git 的原始材料，捕获时应当验证目标文件与选定源文件字节一致，必要时确认源文件在捕获期间没有变化。

一旦材料及元信息进入 GAW commit，Git 已经提供内容寻址、对象完整性和历史记录能力。

因此：

- 不要求每个归档额外保存 SHA-256。
- 不把独立 checksum 作为格式选择的首要条件。
- 不要求归档格式替代 Git 的对象完整性机制。
- 可以保存具有独立用途的文件摘要，例如原有实验校验值或导出时所需的摘要。

应区分源文件捕获时的保真性检查和提交之后的 Git 内容完整性检查。

Git 内容完整性不能证明归档时的源文件选择充分，也不能单独证明归档副本最初与源文件一致。

### 2.4 归档文件与项目历史的关系

GAW checkpoint 的附加 project parents 记录与本次工作相关的项目历史快照。

它们不必与每个归档文件的原始来源一一对应。

例如，一个最初位于 ignored `tmp/` 下的文件，可能是在某次项目 HEAD 上运行实验产生的，但并不是该 HEAD 的 tracked blob。

归档元信息可以描述这一背景；GAW commit graph 则记录有依据的项目快照关联。

不要求在新归档内复制已经由 GAW commit graph 明确表达的 checkpoint 信息。具有独立解释价值的原始文件来源、路径和实验背景仍应保留。

### 2.5 快照内部自解释

每个归档快照应当能够独立解释其内部结构与内容。

这意味着：

- 能识别采用的元信息标准及必要的版本信息。
- 能理解快照整体的主题和用途。
- 能读取文件及其角色描述。
- 必要的文件关系能够通过元信息解析。
- 不依赖另一个归档快照中的专用说明才能解释自身内容。

内部自解释不意味着：

- 必须记录 GAW checkpoint OID。
- 必须重复 Git commit graph 已经表达的历史关联。
- 必须独立于 Git 建立内容校验系统。
- 必须内嵌标准 schema 或 JSON-LD context 的完整副本。
- 必须包含全部实验背景或证明领域描述的真实性。

格式解释所需的外部规范可以由标准版本明确指定，但基本本地创建、读取和验证流程不得要求实时网络访问。

不同历史快照可以采用不同的标准和版本。新格式不要求改写或兼容历史快照内部的旧元信息结构。

## 3. 统一的快照归档模型

### 3.1 每次归档必须创建快照

**GAW 的每次归档操作都必须创建一个独立的归档快照。**

这一要求与选定材料的数量、类型和复杂程度无关。

无论归档的是：

- 单个退役文档。
- 一份临时日志。
- 一个实验脚本。
- 一组实验输入与输出。
- 多个具有共同历史背景的文件。

都必须以快照形式保存。

不允许直接将历史材料散放到 archive workspace 下，也不允许因为只有一个文件就跳过快照元信息。

Archive workspace 可以包含必要的工作区级说明或管理文件，但这些文件不等于归档材料，也不应取代独立快照。

### 3.2 快照的基本结构

每个快照应具有独立目录，其内部至少包含：

- 使用选定标准表示的快照元信息。
- 已选定的原始文件。

原始文件可以是一个，也可以是多个。

概念结构如下：

```text
archive/
├── snapshot-A/
│   ├── metadata
│   └── files/
│       └── GOALS.md
└── snapshot-B/
    ├── metadata
    └── files/
        └── tmp/
            ├── probe.el
            ├── probe.scm
            └── probe.txt
```

这里的 `metadata` 仅为示意，不是规定的文件名。

`files/` 是一种候选布局，并非要求 Data Package 或 RO-Crate 必须采用该目录名。

实际目录布局应由最终选定的标准、工具行为和 GAW 保留原始相对路径的要求共同决定。

### 3.3 原始文件与目录结构

归档快照必须保留选定文件的原始字节内容。

对于来自项目工作树的文件，应保留其相对于原始项目工作树的路径关系。

例如：

```text
tmp/
├── probe.el
├── probe.scm
└── result.txt
```

归档后可以增加固定的包装层，但其内部关系应保持：

```text
snapshot/
├── metadata
└── files/
    └── tmp/
        ├── probe.el
        ├── probe.scm
        └── result.txt
```

不得为了简化元信息而将不同源目录中的文件直接平铺到同一目录。

如果工具需要调整路径表示，必须保证原始相对路径能够被明确恢复。

不要求归档文件继续依赖原始项目工作树才能读取。

### 3.4 快照元信息

每个新快照都必须具有标准化元信息，即使只包含一个文件。

元信息至少应能够表达：

- 快照整体的名称或主题。
- 归档目的或选择理由。
- 已归档文件的身份和路径。
- 必要的文件角色及说明。

其他信息根据具体材料添加，例如：

- 捕获时间。
- 原始相对路径。
- 实验背景。
- 文件之间的关系。
- 已知限制。
- 文件原有状态。
- 独立用途的校验值。

不要求每个快照都具有复杂的关系图，也不要求为简单文档补造不存在的实验背景。

应通过同一种标准支持从简单单文件快照到复杂多文件快照，而不是根据复杂程度切换归档协议。

### 3.5 快照边界与历史演化

每次归档操作创建新的快照目录。

不得将新的归档操作隐式合并进已经提交的旧快照，也不得为了补充材料而直接改写历史 GAW checkpoint。

快照表示一次明确选定并保存的材料集合，而不必是整个项目工作树的完整副本。

如果后续需要保存新增材料、修正描述或形成新的历史记录，应遵循 GAW 的正常 Git 历史与审查要求。

本轮不额外设计快照间的版本继承、合并或替代协议。

### 3.6 历史兼容

现有历史归档不需要迁移。

每个历史 GAW checkpoint 仍按其当时的格式和约定解释。

新的统一快照要求用于后续归档，不构成批量改写既有历史归档的理由。

## 4. 真实验证样本

使用 `ren-lingyu/org-texmacs` 仓库 `_agents` 分支的既有归档实践。

优先选择：

```text
archive/2026-10-06T14-50-30Z--b09b451/
```

并参照：

```text
archive/2026-10-06T16-59-25Z--77a2888/
archive/2026-10-06T17-35-50Z--a242eb2/
```

这些归档主要保存三个相互关联的实验文件，分别承担：

- 实验 runner。
- Native 查询或测试程序。
- 观察结果。

其实际文件名和原始相对路径以对应 `MANIFEST.md` 为准。

现有归档采用如下形式：

```text
archive/
└── YYYY-MM-DDTHH-MM-SSZ--CCCCCCC/
    ├── MANIFEST.md
    └── files/
        └── ... 原始项目相对路径 ...
```

现有 `MANIFEST.md` 已经记录：

- 归档时间。
- 项目状态。
- 实验背景和保存理由。
- 文件原始路径与归档路径。
- Tracked/untracked 状态。
- 文件大小和 SHA-256。
- 文件角色及实验限制。

这些信息构成新格式的比较基准，而不是必须逐字段复刻的规范。

其中项目状态、校验和等信息可以根据新职责边界省略或改用标准字段；文件角色、归档目的及必要实验背景则仍具有独立解释价值。

除了多文件实验快照，还应选取一份普通历史文档，验证单文件快照是否可以使用同一标准，以较少元信息完成创建、读取和检查。

**验证只能在临时目录内进行。不得就地修改原有 archive，亦不得重写相关 GAW checkpoint。**

每种候选格式应基于同一组原始文件创建独立测试副本，以保证比较条件一致。

## 5. 候选标准与工具实现

### 5.1 Data Package 2.0

规范：

https://datapackage.org/standard/data-package/

https://datapackage.org/standard/data-resource/

主要工具：

https://framework.frictionlessdata.io/

实现目录：

https://datapackage.org/overview/software/

Data Package 使用 `datapackage.json` 描述一个 package 及其 resources。

核心优势：

- 标准资源模型较简单。
- 允许任意文件，不限于表格数据。
- 逐文件具有 `name`、`path`、`description`、`sources` 等字段。
- 可选 `bytes`、`hash`。
- 可以通过额外属性保存项目级信息。
- 可直接利用 JSON 工具查看和编辑。

需要注意：

- 并非所有扩展属性都由标准工具提供专门语义校验。
- 资源之间的复杂关系没有与 RO-Crate 等价的通用图模型。
- Frictionless 的通用验证接口可能根据资源类型采用不同处理逻辑，必须对普通文件实测。
- Data Package 1.x 和 2.0 的元信息约定存在差异，不能混淆规范版本。

Data Package 2.0 描述符应显式声明：

```json
{
  "$schema": "https://datapackage.org/profiles/2.0/datapackage.json"
}
```

这里仅展示版本声明，不是一份完整的 Data Package 描述符。

Data Package 2.0 的 `$schema` 是重要的版本标识；不能因为文件名为 `datapackage.json` 或工具可以加载描述符，就认定其符合 2.0。

对于普通非表格文件，不应为了调用表格 API 而错误地将资源声明为表格。

重点调查各实现对 Data Package 2.0 schema 的支持，不能以成功处理较早版本描述符代替 2.0 兼容性验证。

### 5.2 RO-Crate 1.3

规范：

https://www.researchobject.org/ro-crate/specification/1.3/

主要工具：

https://github.com/ResearchObject/ro-crate-py

https://github.com/crs4/rocrate-validator

工具目录：

https://www.researchobject.org/ro-crate/tools/

RO-Crate 使用 `ro-crate-metadata.json`，通过 JSON-LD 图描述归档整体、文件和其他实体。

核心优势：

- 文件和归档整体具有明确的实体模型。
- 可以通过 `@id` 引用其他实体。
- 更自然地表达文件及上下文之间的关系。
- 可以复用已有属性与词汇。
- 不要求每份归档自定义领域 Profile。
- 可以使用标准 JSON-LD 工具处理元信息。

需要注意：

- 最小元信息包含 metadata descriptor、Root Data Entity 等必要结构。
- Root Data Entity 要求 `datePublished`；需要检查该字段在内部 GAW 归档中的合理用法。
- 文件路径以 URI/IRI 表达，对空格、百分号和特殊字符有额外编码要求。
- JSON-LD context、Profile 与验证工具的离线行为必须实测。
- 创建工具支持 1.3，不代表验证器对 1.3 的全部规则均已实现。
- RO-Crate 核心规范并不要求完整列举所有目录文件，也不提供 BagIt 式强制 checksum 机制。

对于 `datePublished`，不得为了通过验证而任意使用源文件创建时间、实验运行时间或项目 commit 时间。

应检查将归档快照的某个生命周期事件解释为发布事件是否合理，并确认其符合规范。

如该字段无法得到合适的语义解释，应明确记录这一适配成本，而不是虚构公开发布日期。

不要因为需要领域词汇就否决 RO-Crate。GAW 不需要归档工具解释实体关系的领域真实性。

同样，不应仅因为 RO-Crate 的图模型更通用，就认为 GAW 必须采用复杂的实体关系描述。

### 5.3 BagIt

规范：

https://www.rfc-editor.org/rfc/rfc8493

BagIt 暂不作为主要候选。

其标准完整性清单仍有价值，但 GAW 当前首要需求是元信息描述，而不是建立一套与 Git 并行的持久内容校验系统。

BagIt 的既有 Python、Go、Java 等实现具有不同的创建、读取和验证能力，但本轮不要求对它们进行与主要候选同等规模的实测。

只有当主要候选在文件保存、基本结构验证或长期维护方面出现明显问题时，才重新评估 BagIt。

### 5.4 工具实现与跨语言差异

**归档标准的选择与具体工具实现的选择相互独立。**

不得将某个标准绑定到特定语言或单一实现。允许组合不同实现承担创建、读取、编辑和验证职责。

工具选型首先考虑功能及标准兼容性，其次考虑 Nix 打包、离线能力、维护成本和依赖复杂度。

实现语言偏好仅作为次要因素；不得为了避免某种语言而接受明显的功能缺失。

#### Data Package 实现

| 实现 | 已知能力 | 主要限制或待验证内容 |
|---|---|---|
| Python `frictionless` | 描述、读取、验证及转换资源，提供 CLI | 通用 API 对普通非表格文件的实际行为；2.0 完整兼容性 |
| TypeScript `frictionless-ts` | Data Package 元数据模型，支持 2.0 风格属性 | 主要面向 Polars 数据处理；非表格资源操作和验证能力待测 |
| JavaScript `datapackage-js` | Package、Resource、Profile、验证、推断等 API | 文档主要使用 1.x 约定；2.0 兼容性不能预设 |
| Go `datapackage-go` | Package 读取、写出、descriptor 验证及非表格资源访问 | 2.0 规范覆盖和依赖维护情况待测 |
| R `frictionless` | 读取、写入 Data Package，提供 2.0 升级支持 | 常规 `add_resource()`、`read_resource()` 主要针对表格资源 |

这些是初步 API 和文档调查结果，不等于已经完成实测。

至少验证 Python Frictionless Framework 与一种非 Python 实现。

优先考虑 `frictionless-ts`、`datapackage-go`，并视 2.0 兼容性调查结果纳入 `datapackage-js`。

R `frictionless` 已有 2.0 升级能力，不能简单归类为只支持旧标准；但其常规资源 API 的表格倾向，需要单独计入 GAW 适用性评估。

特别需要区分：

- 描述符是否能声明普通文件。
- 工具是否能够实际创建普通文件资源。
- 工具是否能够读取普通文件内容。
- 工具能否编辑或保留普通文件的元信息。
- 工具是否会自动将普通文件当作表格解析。
- 工具的验证操作究竟检查资源描述符还是尝试解析数据内容。

某个实现能够处理 Data Package 2.0 的部分字段，不代表它完整实现 2.0 规范。

#### RO-Crate 实现

| 实现 | 已知能力 | 主要限制或待验证内容 |
|---|---|---|
| Python `ro-crate-py` | 创建、读取、目录初始化、添加实体与文件；提供 CLI | 使用的具体版本是否完整支持 1.3 |
| Python `rocrate-validator` | 独立验证器、SHACL、Profile 验证、CLI | 1.3 Profile 覆盖、离线依赖、误报和漏报 |
| Ruby `ro-crate-ruby` | 目录导入、文件操作、读取、写入、自定义实体与引用；声明支持 1.3 | 缺少完整 linked-data 语义验证；默认 HTML preview 行为 |
| JavaScript `ro-crate-js` | JSON-LD 实体编辑、关系引用和基础检查工具 | 验证功能较基础；目录复制和完整归档流程需额外确认 |
| Rust `ro-crate-rs` | 结构化元信息模型，声明支持 1.1–1.3，提供 CLI | CLI 功能受限；与独立验证器的覆盖差异 |
| R `rocrateR` | 创建、读取、编辑、结构检查，支持 BagIt 集成 | 通用文件操作与独立结构验证的覆盖程度待测 |
| Java `ro-crate-java` | Builder API 和实体元信息操作 | 1.3 支持尚未确认 |

这些是初步调查结果，实际功能覆盖仍需核实。

至少验证一种功能较完整的创建实现和一种独立验证器。

优先调查：

- `ro-crate-py`：作为功能和 CLI 的比较基准。
- `ro-crate-ruby`：比较非 Python 实现的完整读写能力。
- `ro-crate-rs`：比较原生 CLI、结构化元信息 API 及版本支持。
- `rocrate-validator`：比较独立标准验证能力。

可以根据实际能力将 `ro-crate-js` 纳入元信息编辑和关系解析测试。

创建与验证可以由不同实现承担。

不得将 `ro-crate-py` 自身的基本文件及元信息操作，误认为已经提供独立验证器的全部 Profile 验证能力。

同样，独立验证器能够验证已有 RO-Crate，不代表它能够负责创建或编辑归档。

#### 功能比较要求

对每个实际测试的工具，分别记录：

- 支持的标准及确切版本。
- 能否创建普通目录形式的归档。
- 能否处理任意纯文本文件，而非仅支持表格资源。
- 能否创建包含单个文件的有效快照。
- 能否读取已有元信息并保留未知扩展属性。
- 能否添加、修改和删除文件的元信息。
- 能否表示及解析实体间引用。
- 能否验证标准结构。
- 是否支持离线运行。
- 是否依赖外部 schema、context 或动态下载。
- 是否生成不需要的附加文件。
- 是否可以通过 Nix 可靠地分发。

区分以下情况：

1. 标准本身不支持某种操作。
2. 标准支持，但当前工具尚未实现。
3. 工具能够实现，但没有直接的 CLI。
4. 工具实现了功能，但使用了不兼容的规范版本。
5. 工具文档声明支持，但尚未经实际测试。

不得将后四种情况混同为标准的固有限制。

#### 语言选择原则

可以使用 Python、Ruby、Rust、Go、JavaScript 或其他语言的成熟实现。

功能完整的 Python 工具优于功能不足的非 Python 工具。

当不同实现的功能、可靠性和维护成本大致相当时，可以优先选择不引入 Python 运行时的实现。

不为了语言统一而要求元信息创建器和验证器必须由同一种语言编写。

## 6. 必须完成的对照验证

### 6.1 最小归档创建

分别使用 Data Package 和 RO-Crate 生成 File URL probe 的标准化副本。

另外，为一份普通历史文档创建单文件快照。

要求：

- 每次归档都生成独立快照。
- 单文件与多文件快照使用相同的元信息标准。
- 原始文件的字节不变。
- 保留原始相对目录结构。
- 元信息格式满足相应规范。
- 尽量使用标准工具的正常创建接口。
- 不引入新的 GAW CLI 命令。

记录每种方案实际需要的文件数量、操作步骤、依赖和代码量。

尤其比较单文件快照的元信息开销，避免为了保存一份普通文本而引入不必要的复杂程序或实体结构。

不能将手写一份表面合法的 JSON 视为创建工具已经通过验证。

如某个工具只提供库 API 而不提供 CLI，可以使用简短的独立调用程序验证，但不能将该程序当作新的 GAW 专用工具实现。

### 6.2 元信息表达

两种候选格式均应尝试表达：

**归档级：**

- 归档名称与主题。
- 捕获时间。
- 归档目的和选择理由。
- 必要的实验背景及局限。

**逐文件：**

- 归档路径。
- 原始相对路径。
- 文件角色。
- 必要的原始状态说明。
- 可选大小及摘要。

优先复用标准字段。

当标准字段不足时，比较增加额外属性、实体或资源所需的工作。

不以扩展字段的数量本身衡量优劣；重点在于这些信息是否容易创建、读取、理解和长期维护。

特别检查：

- 扩展字段的值是否可以使用合适的数据类型。
- 是否需要自定义字段名或词汇标识符。
- 是否存在工具对未知属性的自动删除或重写。
- 是否需要额外的规范文档才能理解文件角色。
- 标准元信息是否已经足以满足后续 agent 的读取需求。

对于单文件快照，不应强制添加与其实际内容无关的实验角色或关联实体。

### 6.3 实体关系验证

使用同一组文件表达：

- Runner 与查询脚本的关联。
- 查询脚本与实验输出的关联。
- 三个文件共同属于同一个历史实验快照。

先检查文件角色描述是否已经足够。

若确实需要机器可读关系，再分别检查：

- Data Package 是否需要自定义引用结构。
- RO-Crate 能否直接使用其实体引用模型。
- 工具能否根据引用读取相关实体。
- 文件改名或路径变化后，需要维护哪些关联。

不要求工具验证这些关系的领域意义。

**如果实际归档只需要逐文件角色描述，那么 RO-Crate 的图模型应视为可选优势，而不是必然需求。**

同样，不应为了证明 Data Package 能表达任意关系而引入一套复杂的自定义引用协议。

比较的重点是 GAW 实际需要的关系能否简单、稳定地表达和读取。

### 6.4 元信息读取

必须通过现成 API 或 CLI 展示：

1. 获取快照级描述。
2. 枚举快照中的文件实体或资源。
3. 查询指定文件的路径及角色。
4. 读取附加的项目级元信息。
5. 在存在结构化关系时找到相关实体。

读取应基于元信息模型，而非自行编写专用的 JSON 路径解析脚本。

允许使用简短的调用示例，但不应通过新建 GAW 私有解析器才能完成基本查询。

如果标准工具只能返回原始 JSON，而没有更高层的资源 API，应记录这是否影响实际工作流，以及使用通用 JSON 工具的成本。

不要求引入专门的服务、数据库或长期运行的元信息索引程序。

### 6.5 结构验证

对标准工具执行正向和负向测试。

| 测试 | 预期 |
|---|---|
| 合法元信息 | 验证通过 |
| JSON 语法错误 | 明确报错 |
| 缺少标准必需字段 | 明确报错 |
| 不合法字段类型 | 明确报错 |
| 无效文件路径 | 能拒绝或报告限制 |
| 被描述的本地文件不存在 | 能检测，或明确区分不在标准校验范围内 |
| 错误的内部实体引用 | 检查工具行为并记录 |
| 合法自定义元信息 | 不应意外丢失 |
| 合法单文件快照 | 验证通过 |

尤其注意：

- Schema 有效性不等于本地文件存在性。
- JSON-LD 有效性不等于实体引用完整性。
- 验证器能解析 Profile 不等于实现了全部相关检查。
- 工具能够读取某个标准版本，不等于能按该版本完整验证。
- 工具的结构检查不等于领域语义真实性验证。

此处只要求清楚界定工具实际提供的结构性保证。

不要求它发现未经选中的其他重要源文件。

### 6.6 文件复制保真性

从源文件创建快照时，实际检查选定文件与目标文件的字节一致性。

至少覆盖：

- 正常复制。
- 目标文件被意外截断。
- 目标内容被修改。
- 源文件在捕获过程中发生变化。

需要明确使用的复制和一致性检查手段，以及发生错误时如何阻止使用不完整的快照。

不要求最终快照携带持久的独立 checksum。

允许在创建过程中临时计算摘要或逐字节比较，但其目标是验证源文件捕获操作，而非建立新的长期内容寻址机制。

验证完成后，才允许对目标快照执行正常的 GAW staging/checkpoint 流程。

不因格式内存在 checksum 字段就跳过捕获保真性检查。

### 6.7 离线与安全边界

两套工具都必须检查：

- 在禁止网络访问时能否创建本地快照。
- 能否离线读取和验证元信息。
- Schema 或 JSON-LD context 是否触发远程获取。
- 是否存在依赖缓存预热才能工作的情况。
- 是否可以禁止资源路径自动下载。
- 是否可能通过绝对路径、`..` 或符号链接访问快照范围外的文件。
- 路径包含空格、Unicode、百分号时能否正确处理。

还应检查：

- 输入目录存在符号链接时的默认处理。
- 元信息引用不存在或位于快照根目录外的文件时的行为。
- 绝对 URI/IRI 是否触发非预期资源访问。
- 读取或验证操作是否具有文件写入副作用。
- 创建过程中发生失败时是否会留下无法识别的部分快照。

不要求 GAW 支持标准允许的所有远程资源功能。

针对 GAW 的本地归档工作流，可以明确限制输入为授权范围内的本地文件。

若工具必须依赖网络才能进行基础本地元信息验证，应视为明显劣势。

如果标准允许远程 schema 或 context，工具可以使用随 Nix 包固定的本地资源，但必须验证实际执行时不会进行远程获取。

### 6.8 NixOS 打包验证

使用项目实际锁定的 nixpkgs，检查：

- 候选工具是否已打包。
- 所需版本能否构建。
- 必要的依赖是否齐全。
- 是否需要独立打包 validator。
- 是否能在固定的离线环境中完成基本操作。
- 是否能够避免在运行时动态下载依赖或资源。

现有调查确认 Python Frictionless Framework、BagIt 以及部分 R 实现有 Nixpkgs 打包记录，但仍须验证实际锁定版本的情况。

RO-Crate 各实现的 Nixpkgs 包属性及版本应逐一确认，不得假定全部已经存在，也不得直接认定其无法打包。

如果需要新增 Nix package，采用正常的固定源和声明式依赖，不允许运行时通过 `pip` 下载。

#### 语言与工具组合

NixOS 打包验证以完整归档工作流为对象，而不是只测试单个库是否能够构建。

允许不同工具分别承担：

- 文件捕获与复制。
- 元信息创建和编辑。
- 元信息读取。
- 标准结构验证。

只有确有必要时才为多个职责引入不同工具。

对每个组合记录完整运行时依赖闭包、构建结果、离线行为和维护成本。

Python、Ruby、Rust、Go、JavaScript 等实现不因语言本身被排除。

当功能与维护成本接近时，可以优先选择不引入 Python 运行时的实现；但独立的 Python 验证器可能仍然是合适选择。

禁止通过 `pip`、`npm`、`cargo install` 或类似运行时包管理操作临时获取正常执行所必需的依赖。

如果需要独立打包，应固定源码、依赖及构建输入，并在可复现的 Nix 环境中验证。

注意区分构建时下载固定源与运行时网络访问。只要构建产物及其依赖已经准备完毕，实际归档操作必须能够离线完成。

### 6.9 跨实现互操作性

为了避免归档快照长期依赖特定工具，增加基本跨实现测试。

每个候选标准至少使用两种独立实现，尽可能完成：

1. 实现 A 创建元信息。
2. 实现 B 读取 A 创建的元信息。
3. 实现 B 查询快照及逐文件属性。
4. 实现 B 修改一个非关键描述字段并写出。
5. 实现 A 重新读取结果。
6. 比较标准字段、扩展字段和内部关联是否得到保留。

若某个实现没有写入能力，允许只进行跨实现读取和验证；必须记录这个限制。

尤其关注：

- 未知扩展属性是否被删除。
- 资源路径是否被重新解释。
- JSON-LD `@id` 与实体引用是否发生意外改变。
- 目录结构是否被修改。
- 工具是否自动重新编码或覆盖原始文件。
- 元信息重新序列化是否产生不必要的大规模变动。
- 是否自动生成 HTML preview、ZIP 或其他非必要文件。

无需保证不同工具产生逐字节相同的元信息文件，但必须保证必要语义不丢失。

验证原始文件内容时仍要求逐字节一致。

如果由于缺少成熟的第二实现而无法完成互操作测试，应明确记录限制，并将其作为工具生态和长期维护风险纳入决策。

不得通过自行编写第二套元信息解析器来人为满足互操作测试要求。

### 6.10 元信息更新与归档快照的不可变性

需要区分归档工具的普通编辑能力和 GAW 对历史快照的使用方式。

标准工具可以具有修改、删除、重新生成元信息的能力，但不因此授权修改已经提交的历史快照。

在验证阶段，应测试工具能否更新尚未提交的测试快照，包括：

- 补充文件描述。
- 修改文件角色。
- 增加或移除内部关系。
- 重新读取并验证更新后的元信息。

同时测试工具是否会意外覆盖未请求修改的其他文件。

对于已经进入 GAW 历史的归档快照，不允许隐式修改其已提交的历史状态。

若之后需要保存新的材料或修正说明，应创建新的快照，并通过正常 GAW checkpoint 记录，而不是在旧快照目录中直接追加文件。

本轮不设计快照继承、替代或版本管理机制，也不要求 GAW 提供专用的 metadata update CLI。

## 7. 选型决策规则

先检查必要条件，再比较相对优势。

### 7.1 必要条件

最终候选必须能够：

- 描述任意普通文件及快照整体。
- 对单文件和多文件快照使用相同的元信息标准。
- 保存 GAW 实际需要的逐文件元信息。
- 用现成工具创建并读取元信息。
- 对标准结构进行基本有效性检查。
- 在授权边界内可靠地保存选定文件。
- 在可复现的 Nix 环境中离线使用。
- 不要求为 GAW 编写完整的专用元信息系统。

无法满足某项要求时，必须说明缺口及补救成本。

这里的必要条件针对完整工具组合，不要求某一个库或 CLI 单独实现所有能力。

### 7.2 优先比较的因素

按以下重要性比较。

**第一优先级：元信息适配程度**

候选模型能否自然表达真实归档所需的信息，而不是依靠大量额外约定。

重点是快照整体、普通文件、文件角色、原始路径和必要关系的表达能力。

同时比较单文件快照的最小元信息复杂度。

**第二优先级：实际工具体验**

创建、读取、检查和修改元信息是否可靠、简单。

需要考虑 CLI/API 的完整程度、功能覆盖、错误处理以及跨实现互操作性。

**第三优先级：实现与维护成本**

比较：

- Nix 打包难度及可复现性。
- 离线运行能力。
- 工具及其依赖的维护状况。
- 运行时依赖闭包的复杂度。
- CLI 与库 API 的可用性。
- 必需辅助脚本和适配代码的规模。
- 长期标准兼容及版本升级成本。

实现语言属于次要偏好。只有在功能、可靠性及维护成本大致相当时，才优先避免 Python。

不得把“已有 Nixpkgs 包”视为功能充分的证据，也不得仅因为某个成熟实现需要额外 Nix 打包，就认定另一个功能不足的现成包更合适。

**第四优先级：结构扩展能力**

是否能够在以后出现明确需求时，方便地表达额外文件关系和上下文。

不能仅因为 RO-Crate 提供更一般的实体模型就判定它更好；也不能因为 Data Package 的结构更简单就预先判定它更合适。

### 7.3 初步选择倾向

根据当前 org-texmacs 实践：

- 如果主要需求是逐文件角色、路径、背景和普通元信息，优先考虑 Data Package。
- 如果实体关系的程序化访问显著改善实际工作流，而且离线验证和 Nix 集成成本合理，优先考虑 RO-Crate。
- 如果两者功能都满足需求，应选择需要更少额外机制、运行更稳定的方案。

这只是初步倾向，不是最终排序。

标准选择与工具选择应分别确定。

最终报告必须分别给出：

- **标准选择**：Data Package 2.0 或 RO-Crate 1.3。
- **创建工具**：负责生成与维护快照元信息。
- **读取工具**：负责恢复快照的结构化描述。
- **验证工具**：负责标准结构检查。
- **文件捕获机制**：负责安全复制及字节一致性检查。

上述职责可以由一个工具承担，也可以由少量互补工具承担。

不得因某个标准的主要创建工具缺少验证能力，就立即认定该标准不可用；应先考察是否存在成熟且能够互操作的独立验证器。

同时不得无条件叠加工具。只有当新增工具提供必要功能时，才接受其依赖和维护成本。

如果非 Python 实现的功能明显不足，而 Python 实现已经满足所有必要条件，则允许直接选择 Python 实现。

当前仅有初步调查结论，尚未完成工具实测，因此不得将某个格式写为 GAW 的正式默认格式。

### 7.4 决策记录

验证后应形成简短的技术报告，包括：

- 标准和工具的确切版本。
- 实验样本及操作方法。
- 单文件与多文件快照的创建结果。
- 每项测试的实际结果。
- 哪些能力来自标准，哪些来自工具，哪些需要项目补充。
- 跨实现互操作结果。
- Nix 打包和离线使用结果。
- 最终选择及放弃其他方案的理由。
- 尚未验证的边界。

必须区分：

- 已经实测的事实。
- 上游文档声明但尚未独立验证的功能。
- 根据规范推导的预期行为。
- 需要 GAW 补充的工作流约束。

如果没有候选达到基本要求，则保留现有快照归档工作流，并报告不足；不因预定开发目标而强制采用新标准。

## 8. 正式实现

只有完成比较并形成决策之后，才修改通用 GAW skill。

### 8.1 更新 archive.md

主要修改：

```text
cabal/share/skills/git-agent-workflow/references/archive.md
```

保留现有关于材料选择、权限、历史引用和 checkpoint 的有效约束。

新增：

- Archive 的职责边界。
- 每次归档必须创建独立快照的要求。
- 最终选定的默认快照格式。
- 快照级和文件级元信息约定。
- 单文件与多文件快照的创建方式。
- 创建、读取和验证的操作步骤。
- 对离线、安全和失败情况的处理。
- 对旧归档的兼容说明。

不要为此修改 GAW Git 协议。

标准元信息与 GAW 语义之间的映射应尽可能简单，不增加与现有 Git 历史职责重复的持久字段。

### 8.2 工具集成策略

优先让 skill 直接调用成熟工具。

只有在实际发现明确功能缺口时，才考虑引入少量 bundled helper。

如果增加 helper，应限定其职责，例如：

- 安全地捕获选定文件。
- 比较源文件与归档副本。
- 调用已有工具生成元信息。
- 检查本地路径边界。

不得自行实现完整 Data Package 或 RO-Crate 解析器、验证器。

工具可作为 archive 工作流的可选依赖，不应无条件进入 `git-gaw` 可执行程序的运行时依赖。

如果最终工具组合包含不同语言实现，应由声明式环境提供所需依赖，不要求用户通过语言包管理器在运行时安装。

### 8.3 分发与验证

如果新增 bundled resources，应更新相应的 Cabal `data-files` 与 Nix 分发检查。

必须检查：

- Source distribution 包含所需资源。
- 安装后的 skill 能正确访问资源。
- 资源引用在安装环境中有效。
- 示例操作不依赖开发 checkout 的路径。
- 必要的 Nix 包能够构建。
- 离线使用符合预期。

不需要为了测试文档中的某一句话而建立脆弱的文本匹配测试；优先验证可观察的工具行为和资源完整性。

如果没有必要的 bundled helper，仅更新 skill 文档即可，不应人为引入新的编译目标或代码模块。

## 9. 历史与项目级兼容

新默认格式只用于后续归档。

不得：

- 批量转换 org-texmacs 旧归档。
- 修改旧的 `MANIFEST.md`。
- 重写旧 GAW checkpoint。
- 为旧归档补造未知来源。
- 修改已经稳定的 archive 路径引用。

历史快照的格式与元信息应按照其创建时的约定解释。

新格式的采用不需要建立统一的历史迁移层，也不要求在一个 archive workspace 下将全部既有材料转换为统一表示。

GAW 通用工作流完成并实际可用之后，另行使用现有 workflow transplantation 指导维护 `org-texmacs-gaw-archive`。

这种维护应把新的工具使用和元信息约定适配进原有项目流程，而不是以删除重复文本为目标。

项目级 skill 仍可保留与该项目有关的证据选择、实验背景、安全边界和用户授权要求。

## 10. 提交组织

建议将本轮分成相互独立的工作单元。

### 阶段 A：调查和验证

在临时目录中完成两种格式的对照实验。

包括：

- 单文件与多文件快照创建。
- 主要候选标准的元信息读取及验证。
- 非 Python 实现与 Python 功能基准的比较。
- 至少一次跨实现读取或验证。
- 文件捕获保真性测试。
- 离线、安全及 Nix 打包验证。

生成可复查的验证记录和决策结论。

在结论形成之前，不修改 GAW archive 的规范性内容。

### 阶段 B：语义与格式规范

独立提交：

```text
docs(skill): standardize archive semantics and format
```

主要修改 `references/archive.md`。

明确统一快照要求、默认格式、工具使用方式及错误处理约定。

### 阶段 C：工具集成

如有必要，独立提交：

```text
feat(skill): integrate archive metadata tooling
```

包括必要的辅助资源、构建或分发检查。

如果已有工具通过 skill 指导即可直接使用，则不需要阶段 C 的代码提交。

### 阶段 D：项目实践移植

在 org-texmacs 项目中单独实施，不混入 GAW 通用 skill 的提交。

不要求将项目级归档格式的历史变化合并为一套统一的存储规范。

## 11. 验收标准

完成本项工作时，应具备：

- 一份支持最终选型的实际验证报告。
- 一种经过验证的默认归档快照格式。
- 所有新归档均以独立快照形式保存。
- 单文件与多文件快照采用统一标准。
- 可复现的创建、读取和结构检查流程。
- 可用的 Nix 工具环境。
- 清晰的源文件捕获保真性要求。
- 独立于 GAW CLI 的元信息操作能力。
- 完整分发且引用有效的 archive skill。
- 对既有归档及 Git 历史的兼容。
- 不引入新的 provenance 真实性或语义充分性保证。

此外，应满足：

- 明确区分标准版本和实现版本。
- 完成至少一种非 Python 实现与 Python 功能基准的对照。
- 完成至少一次独立工具之间的跨实现读取或验证。
- 如采用多个工具，验证其组合能够完成完整快照创建工作流。
- 记录各实现对非表格资源、自定义元信息、实体引用及元信息更新的支持程度。
- 记录工具自动生成的附加文件，以及是否能够禁用。
- 不因实现语言偏好牺牲必要功能。
- 不将尚未经过实际测试的上游功能声明写为已经验证的能力。

**本项工作的核心验收不是“每份归档具有多少字段或校验和”，而是：agent 能否借助现成标准与工具，将每次归档组织为独立、自解释的快照，可靠地保存已选定材料，并让后续 agent 准确读取其结构化描述。**

---

## 12. 不纳入本轮

- 自动判断归档材料是否充分。
- 自动证明来源声明的真实性。
- 自动重现实验。
- GAW archive 专用 Git refs 或新 CLI。
- 统一内容索引或检索数据库。
- 自定义领域本体及强制 Profile。
- 历史归档批量迁移。
- 跨 session/agent 历史整合。
- 修改其他项目的 GAW 历史。
- 为不同归档格式开发统一抽象 API。
- 自行开发通用 Data Package 或 RO-Crate 实现。
- 为归档新增与 Git 并行的持久内容寻址系统。
- 快照之间的继承、合并或替代语义。
